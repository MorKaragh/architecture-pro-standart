Архитектурное решение для обеспечения доступа к ставкам депозитов для кол-центров банка "Стандарт"

### **Функциональные требования**

|**№**|**Действующие лица или системы**|**Use Case**|**Описание**|
| :-: | :- | :- | :- |
|1|Сотрудник кол-центра, Система кол-центра|Получение актуальных ставок|Сотрудник кол-центра получает актуальные ставки депозитов для консультирования клиентов|
|2|Сотрудник партнерского кол-центра, Партнерский кол-центр|Получение файла со ставками|Сотрудник партнерского кол-центра получает файл с актуальными ставками через SFTP|
|3|Менеджер бэк-офиса, АБС|Обновление ставок|Менеджер обновляет ставки депозитов в справочнике АБС|
|4|Система распространения ставок, Система кол-центра|Передача ставок в кол-центр|Автоматическая передача обновленных ставок в систему кол-центра|
|5|Система распространения ставок, Партнерский кол-центр|Передача файла со ставками|Автоматическая генерация и передача файла со ставками через SFTP|

### **Нефункциональные требования**

|**№**|**Требование**|
| :-: | :- |
|1|Доступность системы распространения ставок 99.9%, работа 24/7|
|2|Отклик на запрос ставок < 200ms|
|3|Безопасная передача файлов через SFTP (шифрование)|
|4|Синхронизация ставок в реальном времени между АБС и кол-центрами|
|5|Использование существующих технологий (Java, SFTP, файловые форматы)|
|6|Логирование всех операций передачи ставок|
|7|Валидация данных перед передачей в кол-центры|
|8|Обработка ошибок передачи с retry-механизмом|

**Архитектурное решение:**

*Набор компонентов:*

1. **АБС** - существующая система, источник ставок депозитов
2. **Сервис распространения ставок** - новый микросервис для управления передачей ставок в кол-центры (включает генерацию файлов)
3. **SFTP-сервер** - новый компонент для безопасной передачи файлов партнерскому кол-центру
4. **Система кол-центра** - доработка для получения ставок через API
5. **Партнерский кол-центр** - внешняя система, получает ставки через файлы
6. **Адаптер к АБС** - существующий компонент, источник данных о ставках

*Основные принципы решения:*

- Централизованное управление распространением ставок через единый сервис
- Разделение каналов передачи: API для собственного кол-центра, файлы для партнерского
- Автоматическая синхронизация при изменении ставок в АБС
- Безопасная передача данных с использованием SFTP для внешних систем
- Валидация и логирование всех операций передачи

*Технологические решения:*

- **Сервис распространения ставок**: Java Spring Boot с интеграцией в существующую архитектуру
- **SFTP-сервер**: похоже, можно сделать на базе OpenSSH
- **Формат файлов**: JSON или CSV для удобства обработки партнерским кол-центром
- **Мониторинг**: интеграция с существующей системой мониторинга (Prometheus, Grafana)
- **Логирование**: централизованное логирование через ELK

*Процесс работы:*

1. Менеджер бэк-офиса обновляет ставки в АБС
2. Адаптер к АБС получает изменения ставок
3. Сервис распространения ставок получает уведомление об изменении
4. Для собственного кол-центра: передача ставок через API
5. Для партнерского кол-центра: генерация файла внутри сервиса и передача через SFTP
6. Логирование всех операций для аудита

### **Альтернативы**

**Альтернатива 1: Прямая интеграция кол-центров с АБС**
- Преимущества: Простота реализации, меньше компонентов
- Недостатки: Нарушение принципа изоляции АБС, риск перегрузки системы

**Альтернатива 2: Использование только файлового обмена для всех кол-центров**
- Преимущества: Единый подход к передаче данных
- Недостатки: Неэффективно для собственного кол-центра, задержки в обновлении

**Альтернатива 3: Использование брокера сообщений (Kafka)**
- Преимущества: Высокая производительность, надежность доставки
- Недостатки: Избыточная сложность для текущих требований, партнерский кол-центр не поддерживает API

**Недостатки, ограничения, риски**

**Недостатки:**
- Увеличение сложности архитектуры за счет нового сервиса
- Необходимость поддержки SFTP-сервера
- Дополнительные точки отказа в системе

**Ограничения:**
- Зависимость от формата файлов, поддерживаемого партнерским кол-центром
- Необходимость синхронизации с существующим процессом обновления ставок
- Ограниченная возможность изменения процесса работы партнерского кол-центра

**Риски:**
- Технический риск: сложность интеграции с существующими системами
- Операционный риск: необходимость поддержки дополнительных компонентов
- Риск безопасности: передача файлов через внешние каналы связи
- Риск синхронизации: расхождение данных между системами при сбоях передачи
