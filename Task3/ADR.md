### **Решение**

[C4 диаграмма контекста](C4_diagrams/StandartBank_Context.puml)

[C4 диаграмма контейнеров](C4_diagrams/StandartBank_Containers.puml)

Чтобы не перегружать схемы, на них не отражаются чисто инфраструктурные компоненты, такие как БД, ELK и т.п.
Предполагается что более детально технологический ландшафт опишем в других артефактах, не создавая "великую схему всего и сразу".

**Архитектурное решение:**

*Набор компонентов:*

1. **Сайт банка** - расширение существующего сайта на PHP/React.js для отображения депозитов и приема заявок
2. **Интернет-банк** - доработка существующего ASP.NET MVC приложения для работы с депозитами
3. **Система кол-центра** - доработка для работы через API сервиса заявок
4. **API Gateway** - новый компонент, точка входа в backend для различных интерфейсов (сайт, интернет-банк, колл-центр, админский GUI и т.д.). В перспективе возможно его разделение на специализированные gateway для разных интерфейсов, в MVP обойдемся одним. 
5. **Сервис аутентификации и авторизации** - новый компонент, реализующий аутентификацию и авторизацию (где требуется)
6. **Сервис депозитов** - новый микросервис для обработки заявок на депозиты, их жизненного цикла, а так же реализующий возможности кросс-канальной работы с заявкой (клиент может оставить заявку в нескольких каналах и этот сервис их агрегирует в одну сущность)
7. **Сервис персональных предложений** - новый микросервис для логики расчёта персональных предложений. В перспективе сюда может быть внедрена сложная логика расчета персональных предложений (ML и всё такое)
8. **Сервис уведомлений** - новый микросервис для отправки SMS и функциональности подтверждений SMS-кодом и ПЭП
9. **CRM** - существующий в системе колл-центра модуль, который сейчас не используется. Предлагается задействовать его для ведения клиентской базы. Необходим для построения клиентоцентричной модели данных (частный случай - кросс-канальность заявок на депозит)
10. **Адаптер к АБС** - новый компонент, интеграционный шлюз к АБС для других систем. Скрывает за собой саму АБС, снижает нагрузку на неё с помощью кеширования, позволяет в последствии плавно выносить из АБС все функции, не связанные напрямую с основным банковским учётом.
11. **АБС** - доработка для ведения справочника ставок и обработки заявок


*Основные принципы решения:*

- Разделение слоёв "бизнес-функциональности" (микросервисы) И "учёта" (АБС)
- Использование "адаптера к АБС" для изоляции слоя бизнес-функций от прямого взаимодействия с АБС
- Постепенное снятие с АБС функций, не относящихся к основному банковскому учёту. Нотификации, часть справочников, загрузки excel - все подобное должно в перспективе оттуда уйти. 
- Каждое пользовательское действие, например расчет ставки или подача первичной заявки без подтверждения, не должно приходить в АБС чтобы не создавать ненужную ей нагрузку. Данные из слоя бизнес-функций должны интегрироваться в АБС только после их подтверждения.


*Технологические нюансы:*

- В качестве технологической платформы для новых компонентов используем Java-стэк, с ним в банке уже знакомы. Для GUI - React-стэк.
- Пока избежим внедрения брокеров сообщений - на текущем шаге в нем нет необходимости 
- Отказоустойчивость обеспечивается репликами компонентов в разных ЦОД. В случае, если это не возможно - после завершения MVP стоит запустить проект по поиску решения этой проблемы.
- Для формирования твёрдой технологической базы цифровой трансформации требуется сразу адаптировать ключевые тех.подходы и инженерные практики:
    - unit-тестирование, интеграционное тестирование, quality gate
    - CI\CD
    - логирование и централизованное хранение логов (ELK)
    - мониторинг и алертинг (prometheus, grafana)
    - централизованное хранение конфигураций, безопасное хранение секретов
    - контейнерезация. Возможно, k8s (тут вопрос - потянем ли по компетенциям, кажется что не особо. Готовы платить за администрирование кластера? Я бы на старте не лез туда...)
- Аудит событий в системе на первых порах реализуется на основе логов, выделяется категория Значимых Событий, определяется формат, записи хранятся в отдельном долгосрочном индексе в ELK с обязательными бэкапами
- Кеширование данных (например, справочников ставок) производится in-memory в компоненте "Адаптер к АБС". В перспективе, если кешированных данных станет много, внедрение централизованного кеша и реализация кеширующего слоя на основе Redis или подобного.
- Настоятельно рекомендуется проведение внешнего аудита ИБ по завершению разработки.


### **Альтернативы**
Опишите здесь наиболее важные альтернативные решения.

**Альтернатива 1: Прямая интеграция интернет-банка с АБС**
- Преимущества: Простота реализации, меньше компонентов
- Недостатки: Нарушение требования по избежанию прямой работы с АБС, риск перегрузки АБС

**Альтернатива 2: Полная микросервисная архитектура, переписывание АБС**
- Преимущества: Высокая масштабируемость, изоляция компонентов
- Недостатки: Сложность реализации, несовместимость с текущей версией интернет-банка

**Альтернатива 3: Использование существующей системы кол-центра для всех заявок**
- Преимущества: Единая точка обработки заявок
- Недостатки: Перегрузка системы кол-центра, сложность интеграции с АБС

**Недостатки, ограничения, риски**

**Недостатки:**
- Увеличение сложности архитектуры за счет новых компонентов
- Дополнительные точки отказа в системе
- Вероятная необходимость обучения команды

**Ограничения:**
- Зависимость от существующих технологий банка
- Ограниченная возможность изменения архитектуры интернет-банка
- Необходимость работы в рамках MVP без полной автоматизации

**Риски:**
- Технический риск: сложность интеграции новых компонентов с существующими системами
- Операционный риск: необходимость поддержки дополнительных компонентов
- Временной риск: возможные задержки в реализации из-за сложности архитектуры
- Риск производительности: дополнительные сетевые вызовы между компонентами
- Риск ИБ: возможность утечек данных из-за недостаточной защищенности компонентов при ошибках разработки
